# Architecture

AssessmentFootprint is one local assessment engine with two interfaces. `src/core.ts` owns template persistence, collection, evaluation, run storage, review, evidence/replay access, and report export. `src/templates.ts` validates configuration, derives rule descriptions, and hashes normalized policy contents. `src/cli.ts` invokes the engine directly. `src/server.ts` exposes it to the browser interface in `web/`, with the replay viewer authored in `client/`. Both interfaces therefore use the same templates, validation, assessment records, and criterion semantics.

## Runtime and persistence

Node 24+ runs the engine and CLI TypeScript source directly and supplies `node:sqlite`. FootprintJS `9.44.1` executes and records the evaluation chart. The browser viewer uses pinned `footprint-explainable-ui` `0.38.0`, React/ReactDOM `19.2.5`, and `@xyflow/react` `12.10.2`. These are bundled locally by `scripts/build-viewer.mjs` using esbuild into `web/assets/replay.js` and `replay.css`; no CDN or remote renderer is required. The checkout retains the generated assets. `npm run build:viewer` updates them; `npm run check` verifies that committed bundles match source as well as checking both TypeScript configurations and the tests.

The SQLite database uses WAL mode and stores a JSON payload per run plus versioned template manifests. It is local policy/run storage, not a relational evidence graph or a signed audit service.

The configurable data directory defaults to `.assessmentfootprint` under the process's current working directory. It contains:

```text
assessment.sqlite
assessment.sqlite-wal / assessment.sqlite-shm  (when SQLite creates them)
runs/
  <run-id>/
    inputs/             frozen selected input documents and lockfiles
    <evidence-id>.txt    raw source, scanner output/diagnostics, or workflow JSON
```

Run IDs and evidence IDs are UUIDs. Reports reference these stored artifacts rather than embedding every raw file. A JSON export is an assessment record, not a self-contained evidence archive.

## Template publication and identity

The `template_versions` table has a composite `(template_id, version)` key. SQLite triggers reject update/deletion of published rows. `saveTemplate` validates the draft, opens an immediate transaction, checks the latest saved version against `expectedVersion`, and inserts a new manifest. A new draft without an ID receives a `template-<UUID>` identifier and version 1. Stale edits receive a conflict rather than replacing an existing version. The built-in `oss-readiness` template is seeded as version 1 and is read-only through the API; copying it creates a custom policy.

A manifest contains its name, description, network profile, normalized criteria, creation time, integer version, identity, origin label, and SHA-256 policy digest. The digest is generated through sorted serialization of the name, description, network profile, and criteria. Identity, local version number, and creation time are excluded, so the same normalized policy can have the same digest in another store. Reads revalidate saved configuration and check both its normalized digest and the digest of the actual retained content, so forged derived rule prose cannot pass by being discarded during normalization. These mechanisms enforce consistency in this application's storage path; they do not authenticate an external author or prevent an owner from rewriting the database itself.

The engine import accepts an exported manifest or a draft, revalidates its configuration, and republishes it locally. A custom identifier not present locally starts at local version 1; an existing identifier requires an explicit `expectedVersion` matching the destination's current version and gets the next local version. An exported source version does not supply this concurrency guard. Importing the built-in identifier creates a custom copy. The CLI uses this direct publication path, with `--expected-version N` for an existing destination. The browser import opens a renamed, unpublished copy in its editor and uses ordinary new-template publication, giving it a new identity/history. The incoming digest, creation time, version history, and built-in label are not imported as authenticated provenance.

`resolveRunTemplate` selects a saved manifest and optional exact version. A saved run cannot also choose one-off criterion IDs or a different network profile. Omitting a pinned version selects the latest at run creation. Ad-hoc built-in criterion selection remains supported; its configuration is captured as a one-off policy rather than published as a saved template version.

## Collection and source snapshot

The engine resolves the selected local project folder and captures the selected policy's explicit input paths, plus root `package.json` when present for subject identity. The built-in policy uses root manifests/lockfiles/licence documents and root or `.github` assessment documents. Custom policies can select nested files without recursively scanning unrelated packages. Requested paths are retained even when a file is absent, so scope does not disappear merely because no bytes were captured.

Template path validation rejects absolute/Windows/backslash paths, empty/dot/parent components, and root `.git` inputs case-insensitively. A template is limited to 32 criteria, 32 paths per collector, and 128 unique configured paths across all criteria; shared paths across criteria are counted once. Root package identity is retained separately. File collection resolves paths within the project, rejects symlink escape, accepts only files, and limits each captured input to 8 MiB and the total snapshot to 32 MiB, including package identity. Size is checked before and after reads. Arbitrary source reads outside declared paths are not implied by a template's description.

The captured bytes are copied to `runs/<id>/inputs/` before criteria are evaluated. The snapshot lists each relative path, byte count, and SHA-256 digest, with a digest over the requested-path list and captured-file metadata. This identifies the assessed input set, including requested-but-missing paths; it is not the digest of the entire repository. Optional local Git metadata records the root repository's HEAD through `rev-parse` with filesystem monitoring disabled. The engine deliberately avoids `git status`, which can execute repository-defined filters. `gitDirty` remains `null`; recorded HEAD is contextual metadata and the captured inputs may differ from that commit.

Files used by findings become `EvidenceRecord`s, with a tool identity/version, timestamp, source label, content hash, byte count, artifact reference, and a small structured value. Absent documents are described in the result; absence is not fabricated as a successful source read.

## Evaluation and trace

The built-in `oss-readiness` policy has six criteria, five automatic and one expert, with explicit built-in rule revision `0.1.0`. Custom criteria retain identity/title, description, dimension, evidence requirements, collector, evaluation parameters, and required-review flag. Each run freezes the full chosen template manifest, its digest, selected definitions, and input scope; review and report rendering use those retained definitions rather than silently substituting a newer policy. The engine executes one assessment at a time per engine instance and emits persisted run/criterion start/completion events. Subscriber failures do not alter the run's evidence.

Registered rule forms are built-in policies; file existence with all/any matching and minimum bytes; a field in one JSON document with exists/scalar-equality operators; an OSV finding-count threshold; and attributed expert judgment. Their canonical explanatory text is derived from validated parameters. File/JSON/expert rules use the project-file collector; vulnerability rules use OSV and configured supported lockfile filenames. Evidence requirements preserve up to 20 authored descriptions plus an automatically added attributed-review requirement when applicable. Blank lists are normalized to paths or a single reference to a larger path list; normalized output remains valid input on subsequent reads, edits, and imports. Templates do not supply code, shell commands, arbitrary expressions, plugin modules, or a remotely executed classifier.

JSON traversal checks `Object.hasOwn` at every step. An explicit JSON key named `__proto__` or `constructor` remains ordinary input data; missing inherited properties are never used as evidence. Equality preserves scalar types. Canonical hashing serializes key/value pairs without merging arbitrary JSON into objects or prototypes. Criterion IDs reject reserved object names to keep stage identities safe.

FootprintJS executes the selected evaluation sequence. A chart starts with internal stage `_freeze-inputs`, writing the already captured source digest and an empty findings array; each subsequent asynchronous criterion stage uses its exact criterion ID and writes its active criterion and a summary of the actual result. The engine enables narrative capture and attaches the `metrics()` scope recorder before traversal. It retains the complete `executor.getSnapshot()`, `builtChart.buildTimeStructure`, and `executor.getNarrativeEntries()` in a version-1 `WorkflowRecording` evidence artifact, together with recorder version, assessment ID, policy digest, source digest, and scope `automated-evaluation`. The snapshot includes its execution tree, per-stage writes, commits, write provenance, and recorder data. It does not use an AgentFootprint runtime or pretend that deterministic checks involve a model.

`getWorkflow` reads the stored run, validates its retained policy, verifies the workflow artifact hash through ordinary evidence access, and checks recording format and assessment/policy/source identity. It returns a discriminated `replay`, `legacy`, or `unavailable` response. Full replay has a supported 8 MiB artifact limit. Earlier flat artifacts retain their available narrative with a note naming the absent tree/structure/timings; absent recordings have no fabricated replacement. An integrity mismatch returns a conflict instead of silently rerunning collection or a scanner.

The browser consumes the installed Explainable UI adapters: `graphFromStructure` rebuilds chart nodes/edges from saved structure, `toVisualizationSnapshots` replays recorded commit bundles into cumulative state and reads stage durations from metrics, and `overlayFromSnapshot` derives execution order from commits. The chart IDs, execution IDs, and step state come from the same recording. The state adapter rounds positive durations to integer milliseconds. `client/replay-timing.ts` separately maps the saved Metrics recorder's per-execution durations to timeline presentation with four significant digits, retaining fractional measurements and summing the displayed durations for sequential stage offsets. It does not alter the adapter snapshots or their memory. Exact zero remains measured; a missing, partial, or invalid measurement set uses zero placeholders for the library's untimed execution-order view. All-zero measured runs are explicitly labelled as measured zero rather than missing timing.

Frozen overlay timestamps remain zero and its error map is empty because commits contain neither wall-clock timestamps nor a live error channel. These absent channels must not be presented as recorded telemetry.

Collection completes before the chart starts, so the initial stage is a digest initialization rather than timed file collection. The replay shows recorded automation findings, including a pending human-review status where applicable. Human review updates the current run revision without altering that recording. A displayed execution status of `done` means the stage finished, not that its criterion was satisfied. Scope access and finding evidence IDs help inspect execution; they do not capture every operating-system file read or establish exhaustive file-byte-to-decision causality.

The five status values are `satisfied`, `not_satisfied`, `insufficient_evidence`, `not_applicable`, and `evaluation_error`. Automated rules have deliberately narrow meanings. An expert criterion remains insufficient until a reviewer supplies a decision and rationale. When an automatic rule also requires review, its actual machine outcome is retained as `automaticResult`; the current judgment remains pending until review. `awaiting_review` and `completed` are workflow states; completion is not equivalent to a positive assessment. `automationCompletedAt` records the end of automated evaluation; `completedAt` remains unset while review is pending and is set when the run is finalised.

Each run records its owning process ID. On opening a data directory, the engine detects `running` records whose owner no longer exists, changes them to `interrupted`, and preserves a recovery event and prior evidence. Unexpected run failure also records interruption when a run has already been created. This is recovery of the record, not automatic continuation of scanners or an operating-system-wide job scheduler.

## OSV adapter

The engine probes a native `osv-scanner` executable with `--version` and accepts v2 for dependency assessment. It invokes the executable directly with an argument array, never through a shell. It scans explicit copies of usable configured lockfiles in the frozen input directory and requests JSON, all package records, and disabled Go call analysis. Offline mode supplies `--offline`; preparing the advisory database is a separate operation. OSV 2.6.0 inherits the scanner cache-base environment variable but appends `osv-scalibr/<ecosystem>/all.zip`; do not assume the older documented `osv-scanner` directory suffix applies to that version.

Raw stdout and execution diagnostics are separate evidence artifacts. Missing tools or local advisory data, unsupported versions, invalid JSON, incompatible output, contradictory exit status, or a scan that identifies no packages cannot yield a positive finding. The built-in rule requires zero known vulnerability findings; a custom rule compares the observed finding count against its published maximum. That threshold never changes the original scanner output and does not incorporate severity or reachability. The adapter neither runs `fix` nor installs, builds, tests, or executes the assessed package. Installed dependencies, source reachability, and automatic nested-package discovery are outside its scope; explicitly configured nested supported lockfiles are allowed.

The adapter's offline/online flag governs OSV behavior; it is not an operating-system network sandbox. The complete advisory database is not bundled with a run. Retained raw output supports inspection of this run, while later scans may differ as advisory data changes.

## Human review and reports

Only a criterion requiring review in the run's frozen policy can receive a review. In a SQLite `BEGIN IMMEDIATE` transaction, the engine validates its decision, reviewer name, and rationale, appends a timestamped review with the criterion's evidence IDs, updates the current judgment and completion state, and increments the run revision. A retained `automaticResult` is not rewritten. This serialises review read/modify/write operations across clients sharing the database. The declared reviewer name provides attribution within this local record, not independently verified identity. Prior review entries remain visible; template version and review revision are separate counters.

Evidence access resolves an artifact inside its run directory and checks its SHA-256 digest before returning bytes. A mismatch or escaped path fails the read. This protects the read boundary against accidental artifact changes; it does not establish authenticity if someone can coherently rewrite the local database and files.

Exports verify every referenced evidence artifact and frozen input against its recorded hash before producing output. They also check the retained template policy digest, criterion definitions, framework identity/version/digest, and network profile for consistency. JSON exports preserve the assessment record. HTML exports render its revision, exact captured template, retained rules and evidence requirements, current judgments, retained automatic findings, limitations, evidence index, source snapshot, and review history with escaped text. Neither format is a signed certificate or an independent review, and neither claims JRC certification.

## Local browser boundary

The HTTP server binds to `127.0.0.1`, defaults to a free port, and accepts only its exact local host address. It checks request origins and cross-site browser headers. Mutating requests require a generated per-server session token, supplied by the same local page after bootstrap; this token is a local session boundary, not an account or institutional credential. JSON bodies are bounded to 64 KiB. A static asset allowlist, same-origin content policy, no-store responses, and text evidence responses constrain the browser surface.

The browser can change which local project folder is inspected; the server is not a restricted single-folder filesystem sandbox. Its boundary addresses unrelated websites controlling the local service, not hostile software already acting as the local user. The interface serves its bundled viewer dependencies locally and contains no hosted storage.

## Deliberate first-version boundaries

Saved templates configure the registered rule forms and collectors; they are not a general programmable workflow/DSL or custom command runner. There are no npm-audit/Scorecard adapters, remote repository checks, clone operation, general multi-language inventory, automatic workspace discovery, LLM judging, authenticated reviewer directory, or hosted collaboration. Adding these capabilities must retain explicit source coverage, criterion versioning, real tool outcomes, immutable published policies, and missing-evidence states rather than broadening claims from the existing checks.
